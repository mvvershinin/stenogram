# stenogram-service

REST-декодер стенограмм поверх пакета `stenogram`: очередь задач, S3-хранилище, кэш.
Отдельный дистрибутив — почему, см. [`.docs/decisions/0006-сервис-снаружи-пакета.md`](../.docs/decisions/0006-сервис-снаружи-пакета.md).
Здесь — только как запустить; модель API и формат `blocks.json` — в коде
(`stenogram_service/api.py`, `stenogram_service/blocks.py`) и в примерах ниже.

## Подготовка моделей

Сервис не качает модели сам и не вшивает их в образ — тома. На машине с сетью:

```bash
python -m stenogram.models --fetch --whisper large-v3-turbo
```

Кладёт ONNX-разметку в `~/.cache/stenogram` (`STENOGRAM_HOME`) и whisper в
`~/.cache/huggingface/hub` (стандартный кэш `HF_HOME`). Уже готовый кэш подходит
без пересборки — просто укажите его в `.env` (ниже). Для быстрой проверки без карты
возьмите модель поменьше: `--whisper small` вместо умолчания.

## Запуск

```bash
cp .env.example .env
$EDITOR .env    # STENOGRAM_MODELS_DIR и STENOGRAM_WHISPER_MODELS_DIR — абсолютные пути
docker compose --profile cpu build
docker compose --profile cpu up -d
docker compose ps    # api, minio, worker healthy, minio-init завершился кодом 0
```

`--profile cpu` **обязателен** (не просто «по умолчанию»): без него ни `worker`,
ни `worker-cuda` не поднимутся вовсе — голый `docker compose up -d` даст только
`minio`/`api`. Видеокарта — `--profile gpu` вместо `cpu`, тогда встаёт `worker-cuda`
(стадия `cuda` в `Dockerfile`) вместо `worker`. Профили `cpu`/`gpu` — не «умолчание
и опция», а именно ВЗАИМОИСКЛЮЧАЮЩИЙ выбор: `worker` и `worker-cuda` делят один
бакет кэша и один том задач, оба сразу разбирали бы одну очередь, если бы поднялись
вместе (было багом ревью до разведения по профилям — оба были готовы стартовать
одновременно при `--profile gpu`). **Не проверено на железе** — на этой машине
карты нет, см. `Dockerfile`.

Один образ (`Dockerfile`), три процесса — `api`, `worker`, `worker-cuda` запускают
его разными `command:`/стадиями. `worker`/`worker-cuda` (и `minio`) — в сети
`internal` (`internal: true`): без доступа в интернет вовсе. `api` — в отдельной
сети `edge`: на этом (rootless) докере `internal: true` ломает публикацию порта
начисто (пустой `Gateway`, `ports:` не работает), поэтому `edge` — обычный bridge,
но с отключённым исходящим NAT (`enable_ip_masquerade: false` в `docker-compose.yml`)
— у контейнера нет обратного маршрута наружу, а входящий проброс порта на эту
цепочку не завязан и работает. И `api`, и воркер в сумме без доступа в интернет,
просто разными механизмами (подробности и как проверить — комментарий в начале
`docker-compose.yml`).

**`restart: unless-stopped`** у `minio`, `api`, `worker`, `worker-cuda` (не у
`minio-init` — разовая задача, не демон). Восстанавливает контейнер после
неожиданного падения (OOM, паника рантайма) — но НЕ после `docker compose stop`/
`docker kill`: обе команды Docker считает намеренной остановкой независимо от
сигнала, и `unless-stopped` их специально не трогает (проверено на приёмке: `stop`
— контейнер остаётся `Exited`, `RestartCount` не растёт; форс-килл процесса
ИЗНУТРИ через `docker exec` вообще не работает — PID 1 в своём неймспейсе
игнорирует сигналы от процессов того же неймспейса, это ядро, не наш код; а вот
`docker update --memory` до OOM — настоящее непредвиденное падение — рестарт
срабатывает).

Видеокарта — `docker compose --profile gpu up -d` вместо `--profile cpu` (не
добавочно, а вместо: см. «взаимоисключающие» выше), образ собирается из стадии
`cuda` в `Dockerfile`. **Не проверено на железе** — см. там же.

**Сторож зависания** (`STENOGRAM_STALL_TIMEOUT`, умолчание 900s = 15 минут,
`stenogram_service/config.py`). Пульс воркера (в БД и в alive-файл для
healthcheck) идёт по расписанию независимо от прогресса пайплайна — иначе тихий
этап (отпечатки+кластеризация, штатно без единого события) сочли бы зависшим;
скачивание исходника тоже считается прогрессом — по чанкам (1 МиБ), так что
медленный канал сам по себе не зависание. Но если событий вообще нет дольше
`STENOGRAM_STALL_TIMEOUT` — воркер завершает себя `os._exit(1)`, сразу, без
`finally`. Это не опечатка и не «само пройдёт»: при одном воркере (обычная
топология) звать `recover_stale` некому — тот же процесс, которому положено
это делать, застрял внутри обработки этой же задачи. `os._exit` рвёт процесс
целиком (застрявший `ffmpeg` внутри — тоже, ядро убивает весь PID-неймспейс
контейнера вместе с его init-процессом), `restart: unless-stopped` поднимает
контейнер заново, а задачу без свежего пульса в БД `recover_stale` уже НОВОГО
процесса возвращает в очередь после `STENOGRAM_STALE_AFTER`. Самоисцеления
(возобновиться, если прогресс всё же пришёл) нет — процесса к этому моменту
уже нет. Таймаут на `subprocess.run` ffmpeg внутри пайплайна сторож не
заменяет — это отдельная задача, здесь не трогали.

## Стенд в локальной сети

Сервис на машине с картой, запись на другом компьютере. На сервере в `.env` добавить:

```bash
COMPOSE_FILE=docker-compose.yml:docker-compose.lan.yml
COMPOSE_PROFILES=gpu
STENOGRAM_THREADS=12    # разметке достаётся половина: на 6 ядрах это все 6
```

`docker compose up -d --build` выполняется один раз. Дальше контейнеры поднимает сам
Docker при загрузке машины (`restart: unless-stopped`).

На своём компьютере положить в `~/.config/stenogram/remote.env` адрес и ключи
(`STENOGRAM_HOST`, `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD`) и запускать:

```bash
service/transcribe.sh запись.mp3
```

Стенограмма появляется рядом с записью: `запись.txt` и `запись.blocks.json`. Нужны `curl`
и `jq`. Шумная запись, например из зала суда: `service/transcribe.sh запись.mp3
'{"language": "ru", "denoise": true}'`. Без этого детектор речи теряет большую её часть. API и MinIO открыты всей локальной сети, API без авторизации.

## Пример: POST → GET → rerun

Файл сперва должен лежать в MinIO (`mc cp`, консоль на `:9001`, или SDK). Дальше:

```bash
curl -s -X POST http://localhost:8000/jobs \
  -H 'content-type: application/json' \
  -d '{"source": "s3://stenogram/uploads/совещание.mp4", "language": "ru"}'
# {"job_id": "…"}

curl -s http://localhost:8000/jobs/<job_id>
# {"job_id": "…", "status": "running", "stage": "asr", "fraction": 0.34, ...}
# ...
# {"job_id": "…", "status": "done",
#  "result": {"blocks": "s3://stenogram/stenogram/jobs/<job_id>/blocks.json",
#             "transcript": "s3://stenogram/stenogram/jobs/<job_id>/transcript.txt"},
#  "quality": {"speaker_source": "видео + голос", "speakers": 3, ...},
#  "cache": "miss"}

curl -s -X POST http://localhost:8000/jobs/<job_id>/rerun \
  -H 'content-type: application/json' \
  -d '{"tile_speakers": [2, 1]}'
# {"job_id": "…", "rerun_of": "<родительская задача>"}
```

`result.blocks`/`result.transcript` — адреса `s3://...` в том же MinIO; скачивать
тем же клиентом (`mc cat`, SDK), сервис файлы наружу не проксирует.

## Коды отказов (`GET /jobs/{id}` → `error.code`)

| Код | Значит | `retryable` |
|---|---|---|
| `invalid_params` | параметры задачи не прошли проверку (включая число `tile_speakers`, не совпавшее с числом плиток) | нет |
| `source_not_found` | исходника нет по адресу `source` | нет |
| `source_access_denied` | нет прав на объект в S3 | нет |
| `no_audio` | не удалось извлечь звук (битый/пустой файл) | нет |
| `no_speech` | в записи не нашлось речи достаточной длительности | нет |
| `model_unavailable` | ONNX-модель разметки не на диске, и скачать не вышло (закрытый контур) | нет |
| `storage_unavailable` | S3 недоступен (сеть, таймаут, 5xx) | **да** |
| `worker_lost` | воркер пропал во время обработки (SIGKILL, OOM), попытки исчерпаны | нет |
| `internal` | не классифицировано (включая нехватку памяти) — трейсбек в логе воркера на уровне DEBUG | нет |

`retryable` дублируется в самом ответе (`error.retryable`) — только `storage_unavailable`
имеет смысл повторить тем же телом запроса; остальное лечится сменой параметров.

## Оговорки

**`rerun` по `sha256` не проверяет, что исходник по адресу всё ещё тот же файл.**
Если задача-родитель сохранила `sha256` (парент уже был обработан или ключ известен
заранее), повтор при попадании в кэш распознавания **не скачивает исходник вовсе** —
это и есть смысл кэша. Значит, если файл по тому же `s3://` адресу успели подменить
между исходной задачей и `rerun`, новая задача молча обработает старую версию (из
кэша), а не новую. Если это важно — не полагайтесь на `rerun`, ставьте новую задачу
через `POST /jobs` с тем же `source`: тогда исходник перечитывается и сверяется
заново (`worker.py`, `_execute`: смена `sha256` по тому же адресу логируется и не
считается отказом).

**`/healthz` у `api` требует тот же том моделей, что у `worker`.** Проверка (`models.check_all`)
идёт с настроек самого процесса `api` — если `STENOGRAM_HOME`/`STENOGRAM_WHISPER_DIR`
у `api` и `worker` указывают на разные каталоги, `/healthz` может отвечать `ok`, когда
`worker` реально не сможет загрузить модель, и наоборот. `docker-compose.yml` монтирует
обоим один и тот же том намеренно — не разводите их без необходимости.

**Кэш — по содержимому, не по адресу.** Два разных `source` с одинаковым байтовым
содержимым и одинаковыми параметрами разметки дают одну и ту же запись в кэше
(ключ строится из `sha256`, см. `stenogram_service/cache.py`) — это ожидаемо, а не
утечка данных между задачами: сам документ `blocks.json` не хранит адрес и имена,
их дописывает `for_job` при выгрузке.

**Rootless Docker и права на каталоги моделей.** На rootless-хосте (проверено на
приёмке) UID контейнера переписывается через user namespace: файлы с host-модом,
недоступным «остальным» (например, `600`), контейнер прочитать не может, даже если
владелец на хосте — тот же пользователь. Это безобидно для отдельных файлов кэша
huggingface (`trees/*.json`) — библиотека сама ловит `PermissionError` и просто не
использует кэш-подсказку, в логе воркера остаётся предупреждение, не отказ. Но если
непрочитываемым окажется сам файл или каталог ONNX-модели разметки (без `x` у
«остальных» на каталоге, без `r` — на самом файле модели), `models.check_all`
называет это отдельной строкой «нет доступа к ... (нет прав)» — не путает с «модели
нет вовсе», но и не считает её ошибочно готовой, если файл физически есть, но не
читается. Лечится `chmod o+rX` на каталог и `o+r` на сами файлы моделей.
