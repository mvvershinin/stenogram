## Раздел 2 — Падения на границах входа

Всё воспроизведено на реальном коде, без единой настоящей записи. Это то, что посторонний
встретит в первые полчаса, стоит подсунуть не идеальный файл.

⬜ **Общий перехватчик исключений в `cli.main()`** · 3–4 ч
   Что: перехватчик есть ровно один, вокруг `video.find_tiles` (`cli.py:118-121`).
   Всё остальное всплывает сырым трейсбеком. Пять независимых воспроизведённых триггеров:
   видео без звуковой дорожки (`audio.py:58`), битый файл или нулевая длина (тот же путь),
   тишина целиком (`diarization.py:91`, причём после полной загрузки модели распознавания —
   время потрачено зря), неверный код языка (`ValueError` из faster-whisper через
   `asr.py:36`), недоступный GitHub при первой закачке модели (`models.py:30`). Последнее
   особенно неудачно для домена: записи ВКС судов, а на таких рабочих местах интернет
   часто ограничен. Обернуть тело `main()` после разбора аргументов, переводя
   `RuntimeError`/`ValueError`/`OSError`/`URLError` в строку в stderr и `return 1`,
   по образцу двух уже существующих проверок.
   Проверка: прогнать все пять сценариев — вместо трейсбека одна строка и код возврата 1;
   отдельно убедиться, что `KeyboardInterrupt` не глушится этим же перехватчиком.

⬜ **`estimate_speakers` падает на пустом `np.diff`** · 1–2 ч
   Что: `diarization.py:117-119`, `ValueError: attempt to get argmax of an empty sequence`.
   Два пути, оба воспроизведены. Первый: `--max-speakers 0` роняет **любой вход**, сколько
   бы говорящих ни было, — и это опасно тем, что в том же CLI `--threads 0` означает
   «авто» (`cli.py:74-75`), пользователь попробует по аналогии. Второй: запись с одним
   надёжным отрезком речи и без `--speakers` — короткий монолог или диктовка.
   Вернуть 1 при `len(eigenvalues) < 2`, провалидировать `--max-speakers >= 1` на границе CLI.
   Проверка: регресс-тест с одним эмбеддингом и прогон `--max-speakers 0` и `-1`.

⬜ **`--tile-speakers` короче числа плиток и пустой `_allocate`** · 2 ч
   Что: два падения в одном месте. `IndexError` в `diarization.py:255,258` (`counts[tile]`)
   при `--tile-speakers` короче числа найденных плиток — доступ происходит независимо от
   того, нашлась ли внутри плитки речь. И `ValueError: max() iterable argument is empty`
   в `diarization.py:291`, когда плитки найдены, но подсветка ни разу не поймана уверенно,
   а `--speakers` задан явно. Проверять длину `--tile-speakers` на границе CLI с понятным
   сообщением, защитить `_allocate` от пустого входа.
   Проверка: три прогона — `--tile-speakers` короче числа плиток, `--tile-speakers` длиннее,
   `diarize_with_video(..., video_turns=[], num_speakers=5)`.

⬜ **Создавать каталог вывода при разборе аргументов** · 0.5 ч
   Что: `-o несуществующий/каталог/файл.txt` без `--keep-wav` проходит весь пайплайн
   и падает на последнем шаге (`render.py:131`) — на часовой записи это полчаса впустую.
   С `--keep-wav` та же команда проходит успешно, случайно: `audio.py:49` делает `mkdir`
   побочным эффектом сохранения WAV. Идентичная команда работает или падает в зависимости
   от несвязанного флага. Создавать `stem.parent` при валидации аргументов в `cli.py`.
   Проверка: `-o несуществующий/каталог/имя.txt` без `--keep-wav` — каталог появляется
   до шага «[1/4]», а не роняет пайплайн на последнем.

⬜ **Понизить пиковую память `video.find_tiles`** · 3–4 ч
   Что: `video.py:74` декодирует ~120 кадров в полном разрешении, `video.py:57` приводит
   весь массив к float32. Коэффициент ×4 подтверждён побайтно на 320×240; экстраполяция
   по той же формуле даёт для 1080p ≈3.7 ГБ пиковой памяти и для 4K ≈15 ГБ — до загрузки
   хоть одной модели. На реальном разрешении не замерялось, только расчёт. 1080p —
   обычное разрешение записи созвона. Параметр `count` у `_frames` при вызове из
   `find_tiles` не используется — ограничитель есть, но мёртв. Про 242 МБ звука в проекте
   думали (`del samples`, `cli.py:152`), про кадры — нет. Декодировать с уменьшением
   (`scale=` в фильтре ffmpeg) и не расширять весь массив в float32 разом.
   Проверка: замер пиковой RSS до и после на синтетическом 1080p-ролике
   (`/usr/bin/time -v`); отдельно `/measure`, поскольку правка касается поиска плиток.

## Раздел 4 — Упаковка и установка

⬜ **`pyproject.toml`** · 2–3 ч
   Что: `pip install .` сейчас падает с `ERROR: Directory is not installable. Neither
   'setup.py' nor 'pyproject.toml' found` — воспроизведено в чистом venv. Для стороннего
   человека это выглядит как «проект сломан», хотя `setup.sh` рабочий. Бэкенд —
   setuptools (проект плоский, новый инструмент в `setup.sh` не нужен), `packages =
   ["stenogram"]` явным списком без autodiscovery, версия `dynamic` из
   `stenogram/__init__.py` — тогда `__version__` перестаёт быть мёртвым артефактом и
   становится единственным источником правды. Entry point `stenogram = "stenogram.cli:main"`:
   сигнатура `main(argv=None) -> int` ложится в `console_scripts` без обёртки.
   ffmpeg и модели в `pyproject.toml` не описываются — они и остаются вне `pip`.
   `setup.sh` и `stenogram.sh` не трогаем: `requirements.txt` схлопывается в одну строку
   `-e .`, и `pip install -r requirements.txt` в `setup.sh` продолжает работать дословно.
   Прототип собран и проверен на копии пакета: `pip install -e .`, `stenogram --help`,
   `python -m stenogram --help`, `python -m build --wheel` — колесо чистое, без `docs/`
   и `.claude/`.
   Проверка: `pip install .` в чистом venv → `stenogram --help`; сборка колеса и установка
   его отдельно → тот же дымовой тест; затем офлайн-прогон `HF_HUB_OFFLINE=1 ./stenogram.sh`
   на фрагменте, чтобы убедиться, что переход на editable ничего не сломал в пайплайне.

⬜ **Верхние границы версий и защита от PyTorch** · 1–1.5 ч
   Что: все пять записей `requirements.txt` — только `>=`. Внешняя находка верна, но
   неполна: `faster-whisper` уже сам ограничивает транзитивные пакеты (`ctranslate2<5,>=4.0`,
   `onnxruntime<2,>=1.14`, `tokenizers<1,>=0.13`), их пиннить не надо — получится второй
   источник правды. Реальная дыра — пять прямых записей. Живое доказательство риска:
   `static-ffmpeg>=2.5` уже переехал на мажор 3.0, в репозитории написано 2.5 — просто
   в этот раз повезло. Границы: `faster-whisper<2`, `sherpa-onnx<2`, `numpy<3`,
   `static-ffmpeg<4`, `scikit-learn<2` (временно — уходит целиком по Этапу 0 диеты
   зависимостей, не вкладываться всерьёз). opencv в проекте не используется ни разу,
   пункт снимается.
   Отдельно — вектор возврата PyTorch, конкретный, а не гипотетический: у faster-whisper
   есть `transformers[torch]>=4.23; extra == "conversion"`, у huggingface-hub — свой
   `extra == "torch"`. Сейчас extra не запрошены, torch не ставится. Но достаточно кому-то
   дописать `faster-whisper[conversion]`, скопировав команду из чужого README, — и 2.5 ГБ
   вернутся тихо, до `du -sh venv` никто не заметит. Двухстрочный guard в `setup.sh`
   и отдельным шагом CI превращает принцип решения 0004 из «помним на словах» в «упадёт само».
   Проверка: `pip install .` в чистом venv резолвится без конфликтов; torch-guard даёт
   пусто; понижение любой из пяти границ на патч ниже текущей всё ещё резолвится.

⬜ **Windows и WSL в README** · 0.3 ч
   Что: `setup.sh` на Windows нативно не стартует — нет bash. Про WSL написано в

## Раздел 5 — Тесты

Главное противоречие репозитория: тестов нет ни одного, при этом публикуется вся
`.claude/` — одиннадцать определений агентов и одиннадцать скиллов, включая
`09-test-expert` и `/test-code`. Посторонний прочитает определение агента и пойдёт искать
`tests/`. Заявленная дисциплина без единого теста работает против репозитория сильнее,
чем отсутствие тестов само по себе.

## Раздел 6 — CI

⬜ **Первая волна `ruff` по всему коду** · 1–3 ч
   Что: прогнать `ruff check .` локально и разобрать замечания **до** включения джобы.
   На проекте без конфига и без истории линта первая проверка почти наверняка найдёт
   пачку старых замечаний; если сделать наоборот, первый же PR в новом репозитории будет
   красным не по своей вине. Время непредсказуемо — зависит от того, что найдётся.
   Проверка: `ruff check .` и `ruff format --check .` чисты.

⬜ **`.github/workflows/ci.yml`, три параллельные джобы** · 3–4 ч
   Что:
   `lint` — `ruff check` и `ruff format --check`, ubuntu, без установки зависимостей проекта.
   `test` — `pytest -m "not slow"`, матрица Python 3.10 и 3.12, `apt-get install -y ffmpeg`
   (быстрее и надёжнее, чем тянуть 196 МБ `static-ffmpeg` из GitHub Releases на каждом
   прогоне). Тяжёлые библиотеки мокать не нужно: они импортируются внутри функций,
   а тесты первой волны их не вызывают — ставим полный `pip install -e .[dev]`, цена низкая.
   `install-smoke` — ubuntu и macOS: реальный `pip install .` без `--no-deps` (единственная
   проверка, что дерево зависимостей резолвится сегодняшними границами), torch-guard,
   и `time stenogram --help` как дешёвый регресс-тест на отложенные импорты — `--help`
   обязан отработать за доли секунды, а не ждать ONNX Runtime. Распознавание в CI не гоняем:
   ни моделей, ни записей там нет и не будет.
   Кэш pip по `pyproject.toml`. Оценка времени прогона по весу колёс — 150–180 МБ трафика,
   3–4 минуты стены на весь workflow параллельно.
   Попутная находка, которую обязана ловить именно матрица: свежий `onnxruntime` уже не
   публикует колесо под cp310 в manylinux — заявленный в документации порог «Python 3.10+»
   практически никогда не проверялся.
   Проверка: зелёный прогон в Actions. Минимум один цикл отладки YAML неизбежен.

   Важное условие честности: `pytest` на пустом наборе тестов завершается кодом 5
   («no tests collected»). Джобу `test` включаем только вместе с тестами раздела 5 —
   зелёный бейдж на пустом наборе врёт сильнее, чем отсутствие бейджа.

## Раздел 8 — План развития: в публикацию не входит

Решение: надстройка над стенограммой — **отдельный продукт**, а не следующая версия
инструмента. Репозиторий будет клонирован, работа пойдёт в клоне. В публикацию stenogram
эти файлы не входят.

⬜ **Четыре файла остаются локальными и переезжают в клон** · 0.25 ч

   `.docs/plans/2026-08-23_надстройка.md`. Причины по каждому: первый — конспект другого
   продукта на облачных LLM, и рядом с инструментом, чья первая строка README «ничего
   не отправляется наружу», он бьёт по единственному отличию; второй сам объявлен частично
   отменённым третьим, публиковать оба — публиковать противоречие; третий — R&D-заметки
   по самой необязательной части (архив, приоритет П4); четвёртый — план работ по нулевому
   проценту готовности с оценками в вечерах и открытыми вопросами, по тону рабочий журнал.
   При первом push добавлять файлы явным списком, не `git add -A`.
   Проверка: `git status --short` перед push не показывает их как staged; `git ls-files`
   по их именам пуст после push.

⬜ **Проставить статус-шапку в двух файлах из четырёх** · 0.25 ч
   Что: `.docs/plans/2026-08-23_надстройка.md` уже несёт «Статус: план, работа не начата»,
   у двух других есть хотя бы дата в заголовке. У `docs/идеи-надстройка.md` и

⬜ **Правки раздела 1 сделать до клонирования, а не после** · —
   Что: номер дела и ссылка на каталог с записью уезжают в клон вместе с файлами.

## Чего сознательно не делаем

Решения зафиксированы, чтобы к ним не возвращаться.

⬜ **Не публикуем на PyPI.** `pyproject.toml` нужен для `pip install` из git и исходников,
   не для витрины PyPI: программа при первом запуске качает гигабайты моделей и не
   рассчитана на потребителя, ожидающего самодостаточный `pip install`.
⬜ **Не заводим lock-файл.** Пять прямых зависимостей — дрейф версий не станет проблемой
   раньше, чем через полгода. Понадобится к этапу установщиков.

## Границы: чего эти проверки не доказывают

Чтобы зелёный CI не создавал ложного ощущения.

⬜ Юнит-тесты не проверяют **качество разметки**: согласованность половин реплики, долю
   границ внутри слова, число смен говорящего, распределение долей. Это `/measure` на
   настоящей записи, синтетика намеренно не воспроизводит эхо, перебивания и общий микрофон.
⬜ Тест «значение константы не изменилось» — дешёвый страж от случайной правки, но не
   доказательство, что значение верное. За `stay = 0.80`, `lag = 1.2` и порогом 1.5 с
   стоят замеры из `decisions/`, а не тесты.
⬜ Связность стенограммы читается глазами. Вариант с дроблением на окна прошёл по числам
   и был забракован именно чтением.
⬜ Автооценка числа участников на реальном материале названа в `docs/алгоритмы.md` самым
   хрупким местом пайплайна; тест проверяет только механику на тривиальном случае.
