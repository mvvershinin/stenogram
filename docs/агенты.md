# Команда агентов: как развернуть

В репозитории лежит команда из одиннадцати ролей и одиннадцати команд для Claude Code —
`.claude/agents/` и `.claude/skills/`. Этот документ отвечает на вопрос **как её завести
у себя**. На вопрос **как она работает** отвечают
[`.claude/agents/README.md`](../.claude/agents/README.md) — шпаргалка по ролям и схемам —
и [`.docs/agents.md`](../.docs/agents.md) — полная спецификация.

Проверено на `claude --version` = 2.1.245 (Claude Code). Поведение менялось внутри линейки 2.1.x,
поэтому сверяйтесь со своей версией: спорные места ниже помечены.

---

## Что нужно

- **Claude Code.** Установка одной командой, дальше обновляется сам:
  ```bash
  curl -fsSL https://claude.ai/install.sh | bash      # macOS, Linux, WSL
  ```
  Альтернативы: `brew install --cask claude-code` (без автообновления),
  `winget install Anthropic.ClaudeCode`, `npm install -g @anthropic-ai/claude-code`
  (нужен Node.js 22+). Проверка — `claude --version`.
- **Учётная запись:** платная подписка Claude, либо аккаунт Claude Console с кредитами,
  либо доступ через облачного провайдера. Переменная `ANTHROPIC_API_KEY` заменяет вход
  по логину.
- **Сам проект разворачивать не обязательно.** Агенты — про разработку инструмента,
  а не про его запуск. Но большинство ролей запускает код, так что `./setup.sh` полезен.

---

## Развёртывание

Отдельного шага нет:

```bash
git clone <адрес репозитория>
cd stenogram
claude
```

Определения агентов и навыков подхватываются при старте сессии автоматически. Поиск идёт
от текущего каталога вверх до корня репозитория, поэтому `claude` можно запускать
и из подкаталога.

Перезапуск нужен ровно в одном случае: каталога `.claude/agents/` или `.claude/skills/`
не существовало на момент старта, и первый файл в нём появился уже при работающей сессии.
Если каталог был — правки внутри подхватываются за несколько секунд, без перезапуска.
При клонировании оба каталога уже есть, так что этот случай вас не касается.

## Проверка, что развернулось

```
/skills
```

Должны быть видны все одиннадцать: `develop-asr`, `develop-diarization`, `develop-video`,
`measure`, `orchestrate`, `package`, `privacy-check`, `review`, `roadmap`, `test-code`,
`validate`.

С агентами сложнее: **команда `/agents` списка не показывает** — начиная с версии 2.1.198
это текстовая подсказка, а не панель со списком. Так что проверяйте иначе:

- спросите в диалоге, какие субагенты доступны;
- дайте задачу, подходящую под роль, и посмотрите в транскрипте вызов с нужным
  `subagent_type`;
- `claude plugin validate .claude/agents` — проверяет, что YAML во всех файлах парсится
  (нужна версия 2.1.233 или новее);
- `/doctor` — находит дубликаты имён;
- `claude --debug` — показывает, какие файлы пропущены и почему.

Битый YAML во frontmatter **не даёт видимой ошибки в диалоге** — файл просто молча теряет
метаданные. Узнать об этом можно только через `--debug`. Это главная ловушка при правке
определений.

## Если у вас уже есть свои агенты и навыки

Здесь правила **противоположны** для двух внешне похожих сущностей, и это единственное
место, где легко ошибиться:

| Совпало имя | Кто побеждает |
|---|---|
| Субагент (`code-critic` у вас и в репозитории) | **проектный**, из репозитория |
| Навык (`/review` у вас и в репозитории) | **личный**, ваш из `~/.claude/skills/` |

То есть если у вас есть личный навык с именем `review`, `validate`, `package` или
`orchestrate` — по этой команде запустится ваш, а не проектный. Переименуйте свой либо
вызывайте роль напрямую, попросив Claude делегировать нужному субагенту.

## Разрешения

`.claude/settings.json` в репозитории намеренно нет: команда работает и без него, а любой
общий файл разрешений навязывает выбор всем, кто клонировал.

Если запросы на подтверждение мешают, заведите **свой** `.claude/settings.local.json` —
он в `.gitignore` и остаётся у вас:

```json
{
  "permissions": {
    "allow": ["Bash(pytest *)", "Bash(python -m pytest *)", "Bash(ruff *)"],
    "ask": ["Bash(git push *)", "Bash(pip install *)"]
  }
}
```

`git status`, `git diff` и `git log` разрешены по умолчанию, перечислять их не нужно.

Два неочевидных момента, если вы всё же заведёте общий `.claude/settings.json` в своём
форке:

- **общий проектный файл сильнее личного глобального.** Указав в нём `model`, вы
  переопределите личный выбор каждого, кто клонировал; отменить это человек сможет только
  своим `settings.local.json` в том же проекте;
- **правила `allow` начинают действовать не сразу** — сначала человек должен принять
  диалог доверия каталогу при первом запуске. Правила `deny` и `ask` действуют немедленно.

Файл `settings.local.json`, созданный руками, автоматически не гитигнорится — в этом
репозитории он уже прописан в `.gitignore`, в вашем проекте не забудьте про это сами.

Секретам, токенам и абсолютным путям в общем файле не место — он публичный.

## Формат определений

### Агент — `.claude/agents/<номер>-<имя>.md`

```yaml
---
name: code-critic                      # обязательно: строчные и дефис, без двоеточия
description: Состязательное ревью…     # обязательно: по нему выбирается роль
tools: Read, Grep, Glob, Bash          # необязательно: белый список
model: opus                            # необязательно
---
```

Дальше — текст роли: что читать перед работой, порядок действий, чего не делать.

- **`tools` пропущен — агент получает ВСЕ инструменты**, а не ноль. Это самая частая
  ошибка в понимании. Ограничение нужно задавать явно. В этом проекте оно осмысленное:
  `code-critic` и `architecture-validator` не имеют `Edit` и `Write` — они читают
  и отчитываются, но не правят. `coordinator` единственный имеет `Agent`: только он
  запускает других.
- **`model`** принимает `sonnet`, `opus`, `haiku`, `fable`, полный идентификатор модели
  или `inherit`. Поле пропущено — то же, что `inherit`, то есть модель основной сессии.
  Здесь opus назначен пяти ролям, чья работа требует рассуждения о неочевидном:
  `asr-expert`, `diarization-expert`, `video-expert`, `quality-analyst`, `code-critic`.
  **Если доступа к указанной модели нет — агент не падает**, а тихо поднимается
  на доступной, с предупреждением в интерактивной сессии.
- Файл без `name` определением не считается — он просто документация рядом. Именно
  поэтому `.claude/agents/README.md` лежит в том же каталоге и никому не мешает.

### Навык — `.claude/skills/<имя>/SKILL.md`

```yaml
---
name: review
description: "Состязательное ревью: ищет, чем сломать код…"
user-invocable: true
allowed-tools: Agent, Read, Grep, Glob, Bash
---
```

- **Команда образуется из имени каталога, а не из поля `name`.** Здесь они совпадают,
  так что поле избыточно и безвредно — но переименование папки меняет команду,
  а правка `name` не меняет ничего.
- Обязательных полей у навыка нет вовсе, в отличие от агента.
- `allowed-tools` даёт разрешение без подтверждения **только на тот ход, где вызван
  навык**, а не на всю сессию.
- `user-invocable: false` скрывает навык из меню `/` — он остаётся доступен только самому
  Claude. Не путать с `disable-model-invocation: true`, у которого смысл ровно обратный.
- Имя `synced` зарезервировано.

## Перенос в другой проект

Переносимо: устройство ролей, разделение на технических экспертов, бизнес-роли и контроль
качества, схема «актёр и критик», правило «замер до изменения», ограничение инструментов
для ролей контроля.

Непереносимо и требует переписывания: содержимое ролей. Каждое определение ссылается
на `.docs/domain.md`, `.docs/decisions/` и умолчания этого проекта. Скопированный
`diarization-expert` в чужом репозитории будет ссылаться на несуществующие документы
и защищать чужие числа. Полезен скелет, а не текст.

## Где это работает

Терминал — эталон, всё описанное верно. JetBrains-плагин запускает обычный установленный
`claude`, поведение то же. В панели расширения VS Code доступно **подмножество** команд —
наберите `/`, чтобы увидеть, какое именно. Веб и облачные сессии стартуют с клона
репозитория, поэтому закоммиченные определения работают там так же, как локально,
а личные `~/.claude/` — нет, они остаются на вашей машине.
